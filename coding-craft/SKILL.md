# 编码工艺

## 编码前准备

**动笔之前必须先做三件事，缺一不可：**

1. **读代码** — 浏览要修改的文件及关联文件，理解代码风格和现有模式
2. **找复用** — 搜索已有工具函数、共享模块、通用组件，能复用的优先复用，不要重复造轮子
3. **再动手** — 完成以上两步后才开始写代码

**禁止在未阅读相关代码的情况下直接编写。** 凭猜测写代码是 bug 的主要来源。

## 编码阶段

执行已验证的计划。

- 逐任务按步骤执行
- 测试驱动开发（TDD）
- 每个任务完成后立即提交
- 实现中发现计划有重大缺陷，立即停止并沟通

**代码质量要求：**

- **干净整洁易读。** 变量名、函数名要有语义，不要缩写省略。代码读起来像散文。
- **每段逻辑都必须有注释。** 注释解释为什么（WHY），而非做什么（WHAT）。

**必需子技能：** 使用 superpowers:executing-plans 或 superpowers:subagent-driven-development。

## 自检阶段

**编码后必须验证自己写的代码是否正确。**

- **检查语法** — 运行类型检查 / lint，确认无报错
- **运行测试** — 所有相关测试通过，确认无回归
- **检查可读性** — 代码是否干净整洁、可读性强
- **检查注释** — 是否完备，有无遗漏
- **清理调试残留** — 无 console.log / debugger
- **检查错误处理** — 是否有未捕获的异常路径
- **检查提取空间** — 是否有重复逻辑可以提取为共享工具
- **检查复用遗漏** — 是否有本可复用但未复用的已有代码

**自检不通过不得提交。** 对自己写的代码保持怀疑，不要假设它是正确的。

## 核心原则

- **DRY** — 提取重复逻辑为共享工具
- **YAGNI** — 不为假设的需求提前构建
- **单一职责** — 每个文件、函数、类只做一件事
- **快速失败** — 在边界处校验输入，用清晰的错误信息尽早崩溃
- **显式优于隐式** — 命名导出、类型签名、语义化文件名
- **写完必验** — 不验证正确性不提交
- **干净可读** — 代码像散文一样易读，注释解释为什么

## 速查表

| 维度 | 规则 |
|------|------|
| 命名 | camelCase（变量）、PascalCase（类型/类）、kebab-case（文件） |
| 文件 | 每文件单一职责，最大 200 行 |
| 函数 | 最大 30 行，单出口，0-3 个参数 |
| 导入 | 分组：标准库 → 外部包 → 内部模块，字母排序 |
| 错误处理 | 边界处 try/catch，内部传播类型化错误 |
| 测试 | TDD：失败测试 → 最小代码 → 通过测试 → 重构 |
