# 编码习惯

## 前置要求

**在开始任何编码任务之前，必须先执行 /init 初始化。**

- 如果用户已执行 /init，读取其初始化结果，确认全局 CLAUDE.md 配置已就绪
- 如果用户未执行 /init，**自己执行初始化**：检查项目根目录 `.claude/` 文件夹是否存在，CLAUDE.md 是否已创建
- **严格遵守全局 CLAUDE.md 中的所有规则**，包括沟通原则、Git 操作规范、红线操作、服务器连接配置、项目配置规范等

全局 CLAUDE.md 的优先级高于本技能中的任何规则。当两者冲突时，以全局 CLAUDE.md 为准。

## 五步工作流

每次编码任务严格遵循五个步骤，不可跳过或颠倒。

```
计划 → 验证 → 熟悉 → 编码 → 自检
```

### 第一步：计划

写代码前先制定计划。

- 列出受影响文件的精确路径
- 定义任务之间的接口（消耗什么 / 产出什么）
- 将工作拆分为独立可测试的小任务
- 保存计划到项目级 `.claude/plan.md`

**必需子技能：** 使用 superpowers:writing-plans 生成计划文档。

### 第二步：验证

编码前审查计划的可行性。

- 检查任务边界：每个任务以可测试的交付物结束
- 检查类型一致性：跨任务的名称、签名是否匹配
- 检查占位符：不存在 TODO、TBD 标记
- 检查依赖：无循环引用，无缺失包

**验证方式：** 派发 subagent 审查计划，让其找出漏洞。若无 subagent 可用，则按上述清单自查。

### 第三步：熟悉

**编码前必须阅读现有代码，理解项目结构后再动笔。**

- 浏览受影响文件的代码结构和依赖关系
- 确认现有命名约定、模块划分、错误处理方式
- **优先寻找可复用代码。** 搜索已有工具函数、共享模块、通用组件，能复用的优先复用，不要重复造轮子
- 没有可复用代码时再新建

**禁止在未阅读相关代码的情况下直接编写。** 凭猜测写代码是 bug 的主要来源。

### 第四步：编码

执行已验证的计划。

- 逐任务按步骤执行
- 测试驱动开发（TDD）
- 每个任务完成后立即提交
- 实现中发现计划有重大缺陷，立即停止并沟通

**代码质量要求：**

- **干净整洁易读。** 变量名、函数名要有语义，不要缩写省略。代码读起来像散文。
- **每段逻辑都必须有注释。** 注释解释为什么（WHY），而非做什么（WHAT）。
- 复用优先：先搜已有实现，找不到再新写。

**需求不明确时禁止编码。** 遇到不确定或模糊不清的需求：
- **直接提问澄清**，不要自行猜测
- 或将待确认事项写入计划，标注待讨论
- **绝对不能需求不明确就写代码。** 猜需求写出的代码 100% 需要重写。

**必需子技能：** 使用 superpowers:executing-plans 或 superpowers:subagent-driven-development。

### 第五步：自检

**编码后必须验证自己写的代码是否正确。**

- 运行所有相关测试，确认无回归
- 检查代码是否干净整洁、可读性强
- 检查注释是否完备，有无遗漏
- 检查是否有 console.log / debugger 等调试残留
- 检查错误处理是否完备，有无未捕获的异常路径
- 检查是否有重复逻辑可以提取为共享工具
- 检查是否有本可复用但未复用的已有代码

**自检不通过不得提交。** 对自己写的代码保持怀疑，不要假设它是正确的。

## 核心原则

- **DRY** — 提取重复逻辑为共享工具
- **YAGNI** — 不为假设的需求提前构建
- **单一职责** — 每个文件、函数、类只做一件事
- **快速失败** — 在边界处校验输入，用清晰的错误信息尽早崩溃
- **显式优于隐式** — 命名导出、类型签名、语义化文件名
- **复用优先** — 先搜已有代码，能找到就复用，找不到才新建
- **先读后写** — 不阅读现有代码不写代码
- **写完必验** — 不验证正确性不提交
- **干净可读** — 代码像散文一样易读，注释解释为什么
- **需求不清不问不写** — 不确定就提问或记入计划，绝不猜测
- **遵守全局规范** — 严格遵守全局 CLAUDE.md 中的所有规则

## 速查表

| 维度 | 规则 |
|------|------|
| 命名 | camelCase（变量）、PascalCase（类型/类）、kebab-case（文件） |
| 文件 | 每文件单一职责，最大 200 行 |
| 函数 | 最大 30 行，单出口，0-3 个参数 |
| 导入 | 分组：标准库 → 外部包 → 内部模块，字母排序 |
| 错误处理 | 边界处 try/catch，内部传播类型化错误 |
| 测试 | TDD：失败测试 → 最小代码 → 通过测试 → 重构 |
| Git | Conventional Commits，每次提交一个逻辑变更 |

详细规则见：[代码风格](code-style.md)、[架构模式](architecture.md)、[测试策略](testing.md)、[Git 工作流](git-workflow.md)。
