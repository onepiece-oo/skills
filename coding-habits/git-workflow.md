# Git 工作流

## 分支策略

- **从 `master` 创建功能分支。** 命名：`feat/<简短描述>` 或 `fix/<简短描述>`。
- **绝不直接提交到 `master`。** 即使有推送权限也不允许。
- **分支生命周期短。** 合并后立即删除，单个分支工作不超过 3 天。

## 提交规范

- **每次提交一个逻辑变更。** 如果一次提交涉及两件不相关的事，拆开。
- **Conventional Commits 格式：**

```
<类型>(<范围>): <祈使句主语>

<正文>（可选，非平凡变更时使用）
```

**类型：** `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `ci`

**示例：**

```bash
feat(auth): 添加 JWT 刷新令牌轮换机制
fix(users): 处理个人资料视图中头像为 null 的情况
refactor(payment): 提取验证逻辑到共享模块
test(db): 添加连接池集成测试
```

- **主题行：** 祈使语气、现在时、不超过 50 字符，末尾无句号。
- **正文：** 解释为什么（why），而非做了什么（what）。引用 Issue 编号。

## TDD 过程中的提交序列

```bash
git add src/user.ts tests/user.test.ts
git commit -m "feat(users): 添加用户创建功能和邮箱校验"
```

每个绿色阶段（测试通过）后提交。工作区中不应残留未经测试的代码。

## 拉取请求规范

- **请求审查前自审。** 运行测试、检查 Diff、验证与计划的一致性。
- **PR 描述模板：**

```markdown
## 做了什么
[一句话总结]

## 为什么
[业务原因，而非技术理由]

## 变更
- `src/file.ts`: 添加了 X
- `tests/file.test.ts`: 添加了 Y

## 测试
- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 手动验证：<步骤>
```

- **功能分支使用 Squash Merge。** 保持线性历史。

## 提交前清单

提交前逐项确认：
- [ ] 测试已编写并通过
- [ ] 无 console.log / debugger 语句
- [ ] 无密钥、Token 或 API Key
- [ ] 代码符合命名规范
- [ ] 导入已分组且排序

## 反模式

| 反模式 | 问题 | 修复 |
|--------|------|------|
| 批量提交（"更新"、"修 bug"） | 不可逆、难定位 | 原子提交、清晰的提交信息 |
| WIP 分支长期不动 | 过时、合并冲突 | 每日推送、必要时用特性开关 |
| 重构和功能混在一次提交 | 难审查 | 分开提交 |
| 提交生成的文件 | 仓库膨胀 | .gitignore 构建产物 |
| 在共享分支上强制推送 | 破坏协作者工作 | 绝不在 master 上 force-push |
