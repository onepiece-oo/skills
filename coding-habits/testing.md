# 测试策略

## TDD 工作流

对每段逻辑遵循 RED-GREEN-REFACTOR 循环。

```
红色：写失败的测试 → 确认它失败了
绿色：写最小代码 → 确认它通过了
重构：清理代码 → 确认测试仍通过
```

**永远不要在失败测试之前就写生产代码。** 这保证了测试是有意义的基线。

## 测试金字塔

```
        /\
       /  \      E2E：关键用户旅程（5-10%）
      /----\
     /      \    集成：组件交互（15-20%）
    /--------\
   /          \  单元测试：隔离的业务逻辑（70-80%）
  /------------\
```

- **单元测试：** 快速、隔离、无 I/O。每个测试一个断言。
- **集成测试：** 真实数据库/缓存，外部服务 Mock。测试交互。
- **E2E 测试：** 仅限关键路径。完整栈，真实浏览器或 HTTP 客户端。

## 测试命名

使用 Given-When-Then 模式命名测试：

```typescript
// 正确
describe('UserService', () => {
  describe('createUser', () => {
    it('应该拒绝重复邮箱', () => { ... });
    it('应该在保存前哈希密码', () => { ... });
  });
});

// 错误
it('测试1');
it('正常工作');
```

## Mock 规则

- **仅 Mock 外部服务**（API、支付网关、邮件服务）。
- **绝不 Mock 被测系统本身。** 如果在 Mock 自己的代码，说明设计有问题。
- **优先使用测试替身而非间谍。** 创建显式的测试实现，而非运行时桩。
- **Mock 保持最小。** 只 Stub 测试需要的部分，不 Stub 整个接口。

```typescript
// 正确：显式测试替身
class InMemoryUserRepository implements UserRepository { ... }

// 错误：Mock 自己的代码
jest.spyOn(userService, 'findById').mockResolvedValue(mockUser);
```

## 测试数据

- **工厂函数优于静态 fixtures。** 程序化生成测试数据。
- **测试专用值。** 不使用会掩盖问题的生产默认值。
- **自动清理。** 每个测试获取全新状态，无共享可变数据。

```typescript
function buildUser(overrides: Partial<User> = {}): User {
  return {
    id: crypto.randomUUID(),
    email: 'test@example.com',
    name: '测试用户',
    ...overrides,
  };
}
```

## 覆盖率期望

- **领域逻辑和工具函数：** 分支覆盖率 100%
- **应用/服务层：** 最低 80%
- **关键路径**（认证、支付、数据变更）：无论覆盖率如何，必须有 E2E 测试

## 反模式

| 反模式 | 问题 | 修复 |
|--------|------|------|
| 测试实现细节 | 重构时脆弱 | 测试行为，不测试内部 |
| 每文件一个测试 | 难组织 | 按功能用 describe 分组 |
| 重 Setup 的测试 | 掩盖了测试目标 | 使用工厂函数减少样板 |
| 不稳定测试（Flaky） | CI 信任崩塌 | 确定性数据、正确等待 |
| 没有断言 | 浪费 CI 时间 | 每个测试至少验证一件事 |
