# 编码计划

> **所有输出（计划文档、审查报告、沟通内容）一律使用中文。**

## 前置要求

**在开始任何编码任务之前，必须先执行 /init 初始化。**

- 如果用户已执行 /init，读取其初始化结果，确认全局 CLAUDE.md 配置已就绪
- 如果用户未执行 /init，**自己执行初始化**：检查项目根目录 `.claude/` 文件夹是否存在，CLAUDE.md 是否已创建
- **严格遵守全局 CLAUDE.md 中的所有规则**，包括沟通原则、Git 操作规范、红线操作、服务器连接配置、项目配置规范等

全局 CLAUDE.md 的优先级高于本技能中的任何规则。当两者冲突时，以全局 CLAUDE.md 为准。

**日志文件：** 提到"日志"时默认去项目级 `.claude/` 目录下查找。初始化时在 `.claude/` 目录下创建 `log.log`（短日志）和 `log.txt`（长日志），若已存在则跳过。

## 边界规则

**写计划时绝不碰代码。** 只生成/修改 `.md` 文件，不碰任何源码文件（包括测试文件）。
**一旦切换到编码阶段，绝不改计划。** 编码时严格按计划执行，不随意增删改任务。

**测试和编译由你自行完成。** 计划阶段只负责定义"做什么"，不负责编写或运行任何测试。

## 计划前流程

每次编码任务开始前严格遵循三步流程，不可跳过或颠倒。

```
计划 → 验证 → 熟悉
```

### 第一步：计划

写代码前先制定计划。

- 列出受影响文件的精确路径
- 定义任务之间的接口（消耗什么 / 产出什么）
- 将工作拆分为独立可测试的小任务
- 根据功能命名计划文件，保存到项目级 `.claude/` 目录下，如 `add-user-auth.md`、`fix-login-bug.md`

**必需子技能：** 使用 superpowers:writing-plans 生成计划文档。

### 第二步：验证

**反复审查计划的可行性，不只看一遍。**

至少从以下角度逐一检查，每轮检查一个维度：

1. **完整性** — 规格的每个需求是否都有对应的任务？有没有遗漏？
2. **可实现性** — 每个任务的步骤是否具体到能直接执行？没有 TBD、TODO、"类似任务 N"这类模糊占位符？
3. **一致性** — 后面任务引用的类型名、函数签名、返回值，和前面任务定义的是否完全一致？
4. **依赖关系** — 任务之间是否有循环依赖？有无缺失的包或接口？
5. **大小合理** — 每个任务是否是 2-5 分钟能完成的小步？如果某个任务超过 10 分钟，拆成更小的子任务

**验证方式：** 每次验证后换一种视角重新检查（如：第一次自己看，第二次派 subagent 审查，第三次假装自己是实现者读计划找困惑点）。至少两轮不同视角的检查。

若发现缺陷，回到第一步修改计划，然后重新执行全部验证轮次。

### 第三步：熟悉

**编码前必须阅读现有代码，理解项目结构后再动笔。**

- 浏览受影响文件的代码结构和依赖关系
- 确认现有命名约定、模块划分、错误处理方式
- **优先寻找可复用代码。** 搜索已有工具函数、共享模块、通用组件，能复用的优先复用，不要重复造轮子
- 没有可复用代码时再新建

**禁止在未阅读相关代码的情况下直接编写。** 凭猜测写代码是 bug 的主要来源。

## 提交到编码阶段

完成计划、验证、熟悉三步后，切换到编码环节。**必需子技能：** 使用 superpowers:coding-craft。

## 核心原则

- **先读后写** — 不阅读现有代码不写代码
- **需求不清不问不写** — 不确定就提问或记入计划，绝不猜测
- **计划与代码边界分明** — 写计划不动代码，写代码不改计划
- **所有输出一律使用中文**
- **遵守全局规范** — 严格遵守全局 CLAUDE.md 中的所有规则
