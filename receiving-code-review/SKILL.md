# 代码审查接收

## 概述

代码审查需要技术评估，而非情绪表演。

**核心原则：** 实施前验证。有疑问时先问。技术正确性高于社交舒适度。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整阅读反馈，不要反应
2. 理解：用自己的话重述需求（或提问）
3. 验证：对照代码库现实检查
4. 评估：对此代码库在技术上合理吗？
5. 回应：技术性确认或有理有据的反驳
6. 实施：逐项进行，每项都测试
```

## 禁止的响应

**绝不做：**
- "你说得完全对！"（明确指令文件违规）
- "好观点！" / "出色的反馈！"（表演性的）
- "让我现在就实施"（验证之前）

**应该：**
- 重述技术要求
- 提出澄清问题
- 如果错了用技术理由反驳
- 直接开始行动（行动 > 言语）

## 处理不清楚的反馈

```
如果任何项目不清楚：
  停止 — 不要实施任何东西
  对不清楚的项目提问

为什么：项目可能是相关的。部分理解 = 错误的实施。
```

**示例：**
```
用户："修复 1-6"
你理解了 1,2,3,6。4,5 不清楚。

❌ 错误：现在实施 1,2,3,6，稍后问 4,5
✅ 正确："我理解项目 1,2,3,6。在继续之前需要 4 和 5 的澄清。"
```

## 按来源处理

### 来自你的用户
- **可信** — 理解后实施
- **范围不清楚时仍然要问**
- **不要表演性认同**
- **跳过或技术性确认**

### 来自外部审查者
```
实施之前：
  1. 检查：对此代码库在技术上正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上有效吗？
  5. 检查：审查者是否了解完整上下文？

如果建议似乎不对：
  用技术理由反驳

如果不容易验证：
  说出来："没有 [X] 我无法验证。我应该 [调查/询问/继续]？"

如果与你的用户之前的决定冲突：
  停下来先和你的用户讨论
```

**你的用户的规则：** "外部反馈 — 保持怀疑，但要仔细检查"

## YAGNI 检查"专业"功能

```
如果审查者建议"properly 实现"：
  在代码库中 grep 实际使用情况

  如果未使用："这个端点没有被调用。删除它（YAGNI）？"
  如果使用：然后 properly 实现
```

**你的用户的规则：** "你和审查者都向我汇报。如果我们不需要这个功能，就不要添加它。"

## 实施顺序

```
多项目反馈：
  1. 首先澄清所有不清楚的事项
  2. 然后按以下顺序实施：
     - 阻塞性问题（破坏、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 单独测试每个修复
  4. 验证无回归
```

## 何时反驳

当以下情况时反驳：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对此技术栈在技术上不正确
- 有遗留/兼容性原因
- 与你的用户的架构决定冲突

**如何反驳：**
- 使用技术推理，而非防御性
- 提出具体问题
- 引用通过的测试/代码
- 如果是架构问题，让你的用户参与

**如果你不好意思大声反驳：** 说出这种紧张感，然后向你的用户告知你发现的问题。他们会欣赏你的诚实。

## 确认正确的反馈

当反馈**确实**正确时：
```
✅ "已修复。[简要描述改变了什么]"
✅ "好发现 — [具体问题]。在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "你说得完全对！"
❌ "好观点！"
❌ "感谢指出那个问题！"
❌ "感谢 [任何事物]"
❌ 任何感恩表达
```

**为什么不感谢：** 行动胜于言语。直接修复即可。代码本身就表明你听到了反馈。

**如果你发现自己正要写"谢谢"：** 删除它。陈述修复即可。

## 优雅地纠正你的反驳

如果你反驳了但错了：
```
✅ "你说得对 — 我检查了 [X] 它确实 [Y]。现在实施。"
✅ "验证过了你说得对。我最初的理解错了因为 [原因]。正在修复。"

❌ 长篇道歉
❌ 辩护你为什么反驳
❌ 过度解释

实事求是地陈述更正然后继续。
```

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演性认同 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量实施不测试 | 逐项进行，每项都测试 |
| 假设审查者是对的 | 检查是否会破坏东西 |
| 避免反驳 | 技术正确性 > 舒适度 |
| 部分实施 | 首先澄清所有项目 |
| 无法验证却继续 | 说明限制，请求方向 |

## 实际示例

**表演性认同（错误）：**
```
审查者："删除遗留代码"
❌ "你说得完全对！让我删除那个..."
```

**技术验证（正确）：**
```
审查者："删除遗留代码"
✅ "检查中... 构建目标是 10.15+，这个 API 需要 13+。需要遗留代码以保持向后兼容。当前实现有错误的 bundle ID — 修复它或放弃 13 以下支持？"
```

**YAGNI（正确）：**
```
审查者："使用数据库、日期过滤器、CSV 导出 properly 实现指标跟踪"
✅ "在代码库中 grep — 没有任何东西调用这个端点。删除它（YAGNI）？还是我有遗漏的使用情况？"
```

**不清楚的项目（正确）：**
```
用户："修复项目 1-6"
你理解了 1,2,3,6。4,5 不清楚。
✅ "理解 1,2,3,6。实施前需要 4 和 5 的澄清。"
```

## GitHub 线程回复

在 GitHub 上回复内联审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶级 PR 评论。

## 底线

**外部反馈 = 需要评估的建议，不是需要遵循的命令。**

验证。质疑。然后实施。

从不表演性认同。始终技术严谨。
