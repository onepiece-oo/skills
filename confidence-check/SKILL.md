# 信心检查技能

## 目的

在开始实施**之前**防止错误方向的执行，通过评估信心。

**要求：** ≥90% 信心才能继续实施。

**测试结果**（2025-10-21）：
- 精确率：1.000（无假阳性）
- 召回率：1.000（无假阴性）
- 8/8 测试用例通过

## 何时使用

在实施任何任务之前使用此技能以确保：
- 不存在重复实现
- 架构合规已验证
- 官方文档已审查
- 找到可工作的 OSS 实现
- 根本原因已正确识别

## 信心评估标准

基于 5 个检查计算信心分数（0.0 - 1.0）：

### 1. 没有重复实现？（25%）

**检查：** 搜索代码库中现有功能

```bash
# 使用 Grep 搜索类似函数
# 使用 Glob 查找相关模块
```

✅ 通过：未发现重复
❌ 失败：存在类似实现

### 2. 架构合规？（25%）

**检查：** 验证技术栈对齐

- 阅读 `CLAUDE.md`、`PLANNING.md`
- 确认使用现有模式
- 避免重新发明现有解决方案

✅ 通过：使用现有技术栈（如 Supabase、UV、pytest）
❌ 失败：不必要地引入新依赖

### 3. 官方文档已验证？（20%）

**检查：** 实施之前审查官方文档

- 使用 Context7 MCP 获取官方文档
- 使用 WebFetch 获取文档 URL
- 验证 API 兼容性

✅ 通过：已审查官方文档
❌ 失败：依赖假设

### 4. 引用了可工作的 OSS 实现？（15%）

**检查：** 找到已验证的实现

- 使用 Tavily MCP 或 WebSearch
- 在 GitHub 上搜索示例
- 验证可工作的代码示例

✅ 通过：找到 OSS 引用
❌ 失败：无可工作的示例

### 5. 根本原因已识别？（15%）

**检查：** 理解实际问题

- 分析错误消息
- 检查日志和堆栈跟踪
- 确定底层问题

✅ 通过：根本原因清晰
❌ 失败：症状不清楚

## 信心分数计算

```
总分 = 检查1 (25%) + 检查2 (25%) + 检查3 (20%) + 检查4 (15%) + 检查5 (15%)

如果 总分 >= 0.90:  ✅ 继续实施
如果 总分 >= 0.70:  ⚠️ 呈现替代方案，提问
如果 总分 < 0.70:   ❌ 停止 — 请求更多上下文
```

## 输出格式

```
📋 信心检查：
   ✅ 未发现重复实现
   ✅ 使用现有技术栈
   ✅ 官方文档已验证
   ✅ 找到可工作的 OSS 实现
   ✅ 根本原因已识别

📊 信心：1.00 (100%)
✅ 高信心 — 继续进行实施
```
